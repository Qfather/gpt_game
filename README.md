# 项目开发 README

> 当前阶段开发记录与后续规划\
> 用途：放入 Godot
> 工程中，记录已经完成的系统、当前设计约定以及接下来准备实现的内容。

## 1. 项目核心方向

当前项目以"居民"为基础单位，居民可以从事资源采集，并在后续训练为剑士、弓手等职业单位。

游戏计划结合以下方向：

-   居民生产、采集与资源运输。
-   建筑拥有工人岗位和本地库存。
-   居民可训练为不同职业单位。
-   单位拥有统一的基础属性。
-   单位通过随机"标签 / Trait"产生个体差异。
-   居民出生时随机获得标签。
-   转职或训练为士兵时，可以额外获得职业标签。
-   后续加入类似遗物的全局效果系统。
-   Boss 的全局 Buff / Debuff
    也尽量使用数据驱动的效果系统，而不是把效果硬编码在 Boss 脚本中。

## 2. 已完成：伐木场基础系统

伐木场已经拥有基本生产逻辑。

### 工人系统

已经实现：

-   `max_workers`：最大工人数。
-   `workers`：当前工人列表。
-   `get_worker_count()`：取得当前工人数。
-   `has_free_slot()`：判断是否还有岗位。
-   `add_worker()`：添加工人。
-   `remove_worker()`：移除工人。
-   居民可以被分配为伐木工。
-   无业居民可以返回据点附近待命。
-   伐木场启动时可以寻找空闲居民并分配岗位。

### 工作范围

已经实现：

-   `work_radius`：工作范围。
-   `is_position_in_work_range()`：判断目标位置是否处于伐木场工作范围。

### 伐木场本地库存

已经实现：

-   `storage_capacity`：最大本地木材库存。
-   `stored_wood`：当前木材库存。
-   `get_free_storage()`：剩余容量。
-   `is_storage_full()`：库存是否已满。
-   `deposit_wood()`：向伐木场存入木材。
-   `take_wood()`：从伐木场取出木材。
-   `has_stored_wood()`：判断是否有木材可以运输。
-   UI 可以读取当前库存和最大库存。

### 运输逻辑设计

当前确定的目标流程：

``` text
居民砍树
  ↓
木材送回伐木场
  ↓
伐木场继续累计库存
  ↓
伐木场满仓
  ↓
工人/运输单位将库存搬往据点
  ↓
尽量搬空伐木场
  ↓
重新开始采集
```

重点：不希望只有少量木材时就频繁执行"砍树 → 伐木场 → 据点 →
砍树"的循环。

## 4. 单位基础属性设计

居民、剑士、弓手等单位后续应共享一个统一的单位基础数据/基类。

计划包含的通用属性：

-   最大生命值。
-   当前生命值。
-   生命恢复速度。
-   攻击力。
-   移动速度。
-   食物消耗。
-   其他后续通用单位属性。

设计原则：

``` text
基础单位属性
      ↓
居民 / 剑士 / 弓手 / 其他单位
      ↓
Trait 标签修正
      ↓
装备 / 全局效果 / Boss 效果等进一步修正
      ↓
最终实际属性
```

这样避免居民、剑士、弓手分别重复实现生命值、移动速度等基础逻辑。

## 5. 采集速度设计

采集速度不准备完全写死在伐木场或采石场中。

更合理的方向是：

``` text
单位自身基础工作能力
+
Trait 标签修正
+
建筑生产参数
+
全局 Buff / Debuff
=
最终采集效率
```

例如：

-   伐木场定义木材工作的基础参数。
-   采石场定义石材工作的基础参数。
-   居民自身属性决定个人效率。
-   Trait 可以进一步增加或降低效率。

这样同一个"工作效率高"的居民进入不同资源建筑时仍然能够体现个体差异。

# 6. Trait 标签系统

Trait 是当前重点数据系统。

## 6.1 Trait 与职业的区别

**伐木工不是 Trait。**

伐木工、矿工、剑士等属于职业/工作身份。

Trait 用于描述单位的随机个体特性，例如：

-   飞毛腿。
-   大胃王。
-   强壮。
-   虚弱。
-   剑术天赋。
-   其他正面、负面或混合特性。

目前暂时不开发职业熟练度系统。

------------------------------------------------------------------------

## 6.2 居民出生 Trait

居民出生时计划获得 **1～3 个 Trait**。

生成规则：

``` text
第 1 个 Trait：100%
        ↓
成功获得第 1 个
        ↓
第 2 个 Trait：50%
        ↓
成功获得第 2 个
        ↓
第 3 个 Trait：10%
```

即：

-   第一个必定生成。
-   第二个只有在已经获得第一个后才判定。
-   第三个只有在已经获得第二个后才判定。
-   最终居民至少拥有 1 个 Trait，最多拥有 3 个。

具体概率以后可以继续调整或数据化。

------------------------------------------------------------------------

## 6.3 职业 Trait

居民训练为职业单位时，可以额外获得职业专属 Trait。

例如训练为剑士：

``` text
居民
├─ 原有通用 Trait
└─ 训练为剑士
      ↓
   追加 1～2 个剑士 Trait
```

职业 Trait 与出生通用 Trait 使用分类区分。

当前分类包括：

-   `GENERAL`：通用标签。
-   `SWORDSMAN`：剑士标签。
-   `ARCHER`：弓手标签。

以后新增职业时继续扩展。

------------------------------------------------------------------------

## 6.4 Trait 性质

当前 Trait 性质：

-   `POSITIVE`：正面。
-   `NEGATIVE`：负面。
-   `MIXED`：同时具有优点和缺点。

例如：

**飞毛腿**

``` text
移动速度 +10%
```

**大胃王**

``` text
食物消耗增加
```

**混合型标签**

可以同时：

``` text
攻击力提高
食物消耗提高
```

------------------------------------------------------------------------

## 6.5 Trait 品级

Trait 已加入品级系统：

-   普通 `COMMON`
-   优良 `UNCOMMON`
-   稀有 `RARE`
-   史诗 `EPIC`
-   传奇 `LEGENDARY`

品级主要用于表达 Trait 的稀有程度和价值感。

例如非常强力的 Trait 可以设置：

``` text
传奇
+
较低抽取权重
```

让玩家偶尔获得非常优秀的居民时产生惊喜感。

------------------------------------------------------------------------

## 6.6 Trait 抽取权重

每个 Trait 拥有：

``` gdscript
weight
```

用于同一 Trait 池中的加权随机。

例如：

``` text
普通标签 A：weight = 20
普通标签 B：weight = 10
传奇标签 C：weight = 1
```

不是简单平均随机，而是通过权重控制出现频率。

------------------------------------------------------------------------

## 6.7 Trait 等级

Trait 支持等级数据：

``` gdscript
@export var levels: Array[TraitLevelData] = []
```

同一个 Trait 可以存在不同等级。

例如：

``` text
飞毛腿 Lv.1
移动速度 +5%

飞毛腿 Lv.2
移动速度 +10%

飞毛腿 Lv.3
移动速度 +15%
```

### ICON 方案

为了节省美术资源：

-   同一个 Trait 的所有等级共用一张 ICON。
-   不为 Lv.1 / Lv.2 / Lv.3 分别绘制不同 ICON。
-   后续通过不同等级边框、角标或 UI 表现区分等级。

例如：

``` text
Lv.1 → 普通边框
Lv.2 → 更高级边框
Lv.3 → 高级/发光边框
```

# 12. StatModifier 属性修改系统

已经开始规划独立的属性修改数据结构。

目标是不把 Trait 效果写死成：

``` gdscript
if trait_name == "飞毛腿":
    speed += 10
```

而是使用通用数据：

``` text
属性：MOVE_SPEED
运算：ADD_PERCENT
数值：10
```

这样 Trait Editor 只负责配置数据，单位属性系统负责统一计算。

后续 Modifier 预计至少支持：

-   固定值增加。
-   固定值减少。
-   百分比增加。
-   百分比减少。

例如：

``` text
MAX_HEALTH +20
MOVE_SPEED +10%
FOOD_CONSUMPTION +3
ATTACK_DAMAGE -5%
HEALTH_REGEN +1
```

# 16. Boss 全局效果

Boss 的全局影响计划与遗物使用相同或兼容的效果体系。

区别主要是：

``` text
遗物
→ 通常由玩家获得
→ 多数为正面全局效果

Boss Effect
→ Boss / 地图 / 事件施加
→ 可以是负面 Debuff
```

例如：

``` text
严冬 Boss 效果

所有居民：
移动速度 -10%
工作效率 -15%
食物消耗 +20%
```

Boss 本身只需要引用对应 Effect Resource。

不希望出现：

``` gdscript
if boss == xxx:
    unit.speed *= 0.9
    unit.work_speed *= 0.85
    unit.food *= 1.2
```

而是统一交给数据驱动效果系统。

Trait、遗物、Boss Effect 后续尽量共享底层 Modifier 思路：


# 19. 当前开发原则

为了避免系统后期难以维护，当前确定以下原则：

### 数据与代码分离

脚本负责规则：

``` text
怎么计算
怎么抽取
怎么应用
```

Resource 负责内容：

``` text
叫什么
什么 ICON
什么品级
影响什么属性
数值是多少
```

### 不根据名字判断效果

避免：

``` gdscript
if trait_name == "飞毛腿":
```

应该根据 Modifier 数据计算。

### 职业与 Trait 分离

``` text
职业 = 当前身份/工作
Trait = 个体特征
```

两者不要混为同一个系统。

### UI 不直接负责游戏逻辑

Trait Editor 只编辑数据。

运行时 Trait 系统负责读取和应用数据。

### 优先制作通用系统

新职业、新资源建筑、新 Trait、新遗物和新 Boss
效果应尽可能通过配置扩展，而不是复制大量代码。

# 游戏玩法设计

## 1. 游戏定位

游戏目前确定为 **3D 俯视角 Roguelite 聚落经营 + 自动军事防御**。

玩家的主要身份不是直接操作某一个英雄进行战斗，而是作为聚落的管理者，通过：

-   建造建筑。
-   分配岗位。
-   发展资源产业链。
-   管理居民。
-   训练军队。
-   调整工作区域。
-   设置防御和警戒。
-   应对随机事件。
-   获取随机建筑、研究、Trait 和全局强化。
-   对抗不断升级的裂缝袭击与最终 Boss。

形成每一局都不同的发展过程。

游戏强调
**宏观管理而不是高强度单位微操**。居民和士兵拥有自己的行为逻辑，玩家主要决定"谁去做什么、在哪里做、聚落如何发展"。

------------------------------------------------------------------------

## 2. 单局核心循环

目前设想的一局流程：

``` text
随机生成地图
      ↓
建立初始据点
      ↓
获得基础居民
      ↓
探索周围资源
      ↓
建立伐木场 / 采石场 / 其他生产建筑
      ↓
居民自动采集、运输、吃饭、工作
      ↓
获得随机建筑蓝图 / 研究 / 强化选择
      ↓
逐步建立资源产业链
      ↓
训练居民成为剑士 / 弓手 / 其他职业
      ↓
裂缝开启
      ↓
敌人多波袭击
      ↓
防守成功并继续扩张
      ↓
新的资源、事件、强化与更强袭击
      ↓
最终 Boss 裂缝
      ↓
Boss + 全局规则 / Debuff
      ↓
完成本局
```

目标单局时长暂定约 **20～50 分钟**。

------------------------------------------------------------------------

## 3. 时间控制

作为聚落经营与自动战斗游戏，计划支持时间速度控制：

``` text
暂停
1×
2×
3×
```

玩家可以在规划建筑、查看居民、处理事件时暂停，在稳定生产阶段加速。

这样游戏重点可以放在决策，而不是要求玩家持续快速操作。

------------------------------------------------------------------------

## 4. 据点

据点是整个聚落的核心。

当前已经在居民逻辑中使用据点作为无业居民的待命位置。

后续据点还会承担：

-   聚落核心。
-   主要资源储存。
-   居民待命区域。
-   居民吃饭地点。
-   可能的居民出生/加入位置。
-   生产建筑运输资源的最终目的地。
-   防守失败的重要目标之一。

无业居民不应该永久站在原地，而是返回据点附近形成自然的聚落活动。

------------------------------------------------------------------------

## 5. 居民

所有基础人口首先都是"居民"。

居民是整个经济和军事系统的基础资源。

居民可以：

``` text
居民
├─ 无业 → 据点附近待命
├─ 进入伐木场 → 从事伐木
├─ 进入采石场 → 从事采石
├─ 进入其他生产建筑 → 对应工作
└─ 进入训练建筑 → 训练为军事职业
```

居民之间通过随机 Trait 产生差异。

因此玩家获得的新居民并不完全相同，例如：

``` text
居民 A
飞毛腿 Lv.2
移动速度较快

居民 B
大胃王 Lv.1
食物消耗较高

居民 C
强壮 Lv.3
生命值和劳动/战斗能力更优秀
```

这使人口本身也具有一定 Roguelite 随机性。

------------------------------------------------------------------------

## 6. 职业与训练

职业和 Trait 是两个独立系统。

### 职业

表示单位当前身份，例如：

-   居民。
-   伐木工。
-   矿工。
-   剑士。
-   弓手。
-   后续其他职业。

### Trait

表示这个单位本身的个体特点。

例如：

-   飞毛腿。
-   大胃王。
-   强壮。
-   虚弱。
-   剑术天赋。

居民可以从事生产工作，也可以被训练为军事单位。

例如：

``` text
居民
  ↓
训练
  ↓
剑士
  ↓
保留原有通用 Trait
+
额外获得 1～2 个剑士职业 Trait
```

这样同样是剑士，也可能因为出生 Trait 和训练 Trait 不同而拥有不同表现。

目前暂时 **不制作职业熟练度系统**，先把
Trait、职业、生产和战斗主循环做完整。

------------------------------------------------------------------------

## 7. 自动生产玩法

生产单位以自动行为为主。

伐木流程目前已经形成：

``` text
寻找树木
  ↓
移动到树木
  ↓
砍树
  ↓
携带木材
  ↓
返回伐木场
  ↓
存入伐木场本地库存
  ↓
继续工作
```

当生产建筑库存达到运输条件后：

``` text
伐木场满仓
  ↓
停止单纯累积
  ↓
将库存运往据点
  ↓
尽量搬空本地库存
  ↓
恢复采集
```

后续采石场等生产建筑复用类似框架，只替换资源类型、采集对象和工作参数。

------------------------------------------------------------------------

## 8. 食物与居民需求

居民不是永久无消耗工作的机器。

后续计划加入食物需求：

``` text
居民工作
  ↓
消耗食物 / 饥饿增加
  ↓
达到吃饭条件
  ↓
返回据点
  ↓
消耗聚落食物
  ↓
吃饭
  ↓
重新返回工作岗位
```

Trait 会影响这个循环。

例如：

``` text
大胃王
→ 食物消耗提高

节食类 Trait
→ 食物消耗降低
```

这样人口越多并不只是纯收益，也会增加聚落的后勤压力。

------------------------------------------------------------------------

## 9. 资源与产业链

游戏不会只停留在"砍木头"。

当前伐木场是第一套用于验证系统的资源建筑。

后续计划逐渐加入：

``` text
自然资源
   ↓
基础采集建筑
   ↓
本地库存
   ↓
运输到据点 / 仓库
   ↓
加工建筑
   ↓
高级资源
   ↓
建筑 / 训练 / 防御 / 强化
```

生产建筑应尽量使用统一接口。

例如：

-   当前库存。
-   最大库存。
-   当前工人数。
-   最大工人数。
-   工作范围。
-   生产效率。
-   资源类型。

这样采石场等建筑可以复用已经完成的建筑 UI 和工人逻辑。

------------------------------------------------------------------------

## 10. 随机建筑与研究

Roguelite 随机性不只来自居民 Trait。

单局发展计划加入随机的建筑蓝图、研究或强化选择。

例如在阶段性发展过程中出现：

``` text
三选一

[新的生产建筑]
[军事研究]
[经济强化]
```

因此玩家不一定每局都能按照完全相同的固定科技路线发展。

某一局可能更适合：

-   快速经济。
-   大量居民。
-   强化剑士。
-   远程防御。
-   高效率资源链。
-   依赖某种特殊遗物或 Trait 组合。

------------------------------------------------------------------------

## 11. 裂缝袭击

地图中的主要外部威胁来自"裂缝"。

裂缝会随着游戏进程出现并产生敌人。

一次袭击不一定只有一波，而是可以：

``` text
裂缝出现
  ↓
第一波
  ↓
短暂间隔
  ↓
第二波
  ↓
第三波
  ↓
精英 / 特殊敌人
```

随着单局推进：

-   袭击强度提高。
-   敌人种类增加。
-   特殊能力增加。
-   对聚落不同区域产生压力。

玩家需要在发展经济与准备下一轮防守之间做取舍。

------------------------------------------------------------------------

## 12. 防御不是单纯围墙玩法

城墙是防御手段之一，但不能成为万能答案。

敌人后续可以拥有不同突破方式，例如：

-   正面攻击城墙。
-   飞越城墙。
-   跳墙。
-   传送进入内部。
-   从地下钻入。
-   潜入聚落。
-   绕开防御。
-   攻击不同目标。

不同敌人的目标也不一定完全相同。

例如可能存在：

``` text
攻击据点型
攻击居民型
攻击资源建筑型
破坏防御设施型
特殊目标型
```

这样玩家不能只造一圈墙就永久解决防守问题，而需要考虑：

-   防御纵深。
-   军队部署。
-   警戒区域。
-   建筑布局。
-   重要建筑保护。
-   对特殊敌人的针对手段。

------------------------------------------------------------------------

## 13. 军队控制方式

游戏不计划变成传统 RTS 的高频微操。

玩家主要通过宏观命令控制军队，例如：

-   设置警戒区域。
-   设置防守位置。
-   调整单位岗位。
-   指定大致作战区域。
-   设置优先保护目标。
-   调整部队构成。

士兵自身负责：

-   寻敌。
-   移动。
-   攻击。
-   基础战斗行为。

目标是让玩家把注意力放在"聚落如何应对问题"，而不是持续框选单位点地板。

------------------------------------------------------------------------

## 14. Boss 裂缝

一局后期计划出现最终 Boss 裂缝。

Boss 不只是一个血量更高的大怪。

Boss 可以给整局施加特殊的 **全局规则 / 凝视 / Debuff**。

例如：

``` text
严冬 Boss

全体居民：
移动速度 -10%
工作效率 -15%
食物消耗 +20%
```

或者 Boss 改变某些基本规则，使玩家必须临时调整经济和防御方式。

因此 Boss 战从出现前就已经开始影响玩家的聚落规划。

------------------------------------------------------------------------

## 15. 遗物系统

后期计划加入类似《杀戮尖塔》遗物的全局强化。

遗物可以改变整个聚落，而不是只修改一个居民。

例如：

``` text
丰收图腾
所有居民工作效率 +10%

军团旗帜
所有剑士攻击力 +15%
```

遗物也可以成为单局构筑的重要组成部分。

不同遗物 + 不同建筑 + 不同居民 Trait +
不同职业组合，可以让每一局形成不同的发展方向。

------------------------------------------------------------------------

## 16. Boss Effect 与遗物共用底层效果系统

遗物和 Boss Debuff 在设计上方向相反，但底层可以共用
`StatModifier / Effect`。

``` text
                 Effect / StatModifier
                         │
             ┌───────────┴───────────┐
             ↓                       ↓
           遗物                   Boss Effect
             ↓                       ↓
         正面全局强化             负面全局规则
```

Boss 脚本只负责：

``` text
Boss 出现
→ 激活对应 Effect
```

Boss 死亡或规则结束：

``` text
→ 移除对应 Effect
```

不在每个 Boss 中重复编写居民速度、食物消耗、攻击力等修改代码。

------------------------------------------------------------------------

## 17. Roguelite 随机性的来源

目前计划让一局中的随机性来自多个层面：

### 地图

-   地形。
-   资源分布。
-   可扩张方向。
-   裂缝位置。

### 居民

-   出生 Trait。
-   Trait 数量。
-   Trait 品级。
-   Trait 等级。
-   职业训练 Trait。

### 发展

-   建筑蓝图。
-   研究。
-   强化选择。

### 全局构筑

-   遗物。
-   特殊事件。
-   Boss 全局规则。

最终希望形成：

``` text
地图随机
+
居民随机
+
建筑/研究随机
+
Trait 随机
+
遗物随机
+
敌人与 Boss 规则变化
=
每局不同的发展过程
```

------------------------------------------------------------------------

## 18. 玩家主要决策

游戏希望玩家主要思考这些问题：

-   现在应该继续扩张经济还是准备防守？
-   新居民应该投入生产还是训练为士兵？
-   哪些资源最紧缺？
-   哪个建筑值得优先建造？
-   哪些居民 Trait 更适合某类工作？
-   当前人口增长是否会导致食物压力？
-   下一次裂缝前能否完成新的防线？
-   军队应该保护据点还是外围生产建筑？
-   当前获得的随机研究/遗物应该如何利用？
-   Boss 的全局 Debuff 会迫使我改变什么？

重点是
**系统之间互相产生压力和选择**，而不是单独堆很多互不相关的小功能。

------------------------------------------------------------------------
