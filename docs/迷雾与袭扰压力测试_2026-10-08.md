# 迷雾与袭扰压力测试（2026-10-08）

本文帧率与热点数据采自同日瞭望塔实现之前，当时普通居民仍主动搜敌并争抢避难位。随后已改为统一警报、受击触发和固定回住所，2026-10-09又将独立瞭望塔合并到箭塔，见[箭塔规则](箭塔警戒与居民避险.md)。复跑当前脚本会使用新玩法，不能直接当作相同行为的性能对照。

## 测试方法

使用 `Tests/fog_raid_stress_test.gd`，在有画面的 Forward+ / D3D12 游戏进程中运行。固定地图种子 418、40×40 地图、568 个资源，禁用后续人口和关卡事件生成。保留真实单位 AI、碰撞、导航、采集、攻击、受击特效和避难流程。测试提高生命值到 100000，避免测试期间死亡减少负载；不修改游戏资源文件。

测试设备：Intel Core i5-10400F、NVIDIA GeForce GTX 1650，Godot 4.7.2。计时子类有少量测量开销，结果主要用于同一工具内的对照和热点定位。

每局增加农场、伐木场、猎人小屋和住房各一座。3 名农民、3 名伐木工、1 名猎人，其余居民中每 5 人设 1 名剑士。人口密集分布于据点附近。这是人为拥挤的压力布局，不是用户原来的第 19 分钟存档。

测试顺序为：正常工作 240 帧、敌人出现与避难 360 帧、持续战斗 360 帧、保持当前遮罩并暂停迷雾刷新 360 帧、再暂停单位 AI 360 帧。除启动外，各阶段记录真实帧间隔；P95 表示 95% 的帧耗时不超过该值。显示器约 75 Hz，正常运行约 13.3 毫秒一帧；不能据此测出未限帧的最大吞吐量。

各对照阶段按顺序运行，游戏状态会继续演进，不是同一存档瞬间的严格重放。暂停迷雾刷新是诊断操作，会暂时冻结显隐和视野判定，不能作为正式优化方案。持续战斗阶段与后续暂停阶段适合判断大幅性能差异，不能把差值直接当作精确的函数成本。

## 分段计时

计时只在测试子类中记录，游戏生产脚本不增加统计开销：

- 迷雾总刷新时间，以及树木数据收集、遮挡角度、角度平滑、像素合并、树冠修补、对象显隐。
- 其余时间包括视野源整理、数组/图像复制和纹理提交。这里测的是 CPU 提交时间，不是 GPU 完成上传和渲染的耗时。
- 居民物理脚本、移动导航、避难选址；敌人物理脚本、移动导航与每帧选敌。
- 导航和避难选址是居民脚本的子项，敌人导航是敌人物理脚本的子项，不能与父项相加。
- 后续 66 人的 1 倍速与 3 倍速对照另统计每渲染帧的居民物理调用次数除以居民人数，估计每帧物理更新次数，以及超过 33、66、142.857 毫秒的帧数。

## 复测

在项目根目录依次运行，避免多个游戏压力进程互相干扰：

```powershell
godot --path . --script res://Tests/fog_raid_stress_test.gd -- --population=11 --speed=3
godot --path . --script res://Tests/fog_raid_stress_test.gd -- --population=33 --speed=3
godot --path . --script res://Tests/fog_raid_stress_test.gd -- --population=66 --speed=3
godot --path . --script res://Tests/fog_raid_stress_test.gd -- --population=66 --speed=1
```

`godot` 替换为本机 Godot 4.7 可执行文件。不要添加 `--headless` 作为帧率验收。初始五阶段测试结果保留在 `.godot/fog_raid_stress_人数_倍速x.json`；最新脚本已增加单位细分计时和绕过避让的诊断阶段，当前输出为 `.godot/unit_profile_stress_人数_倍速x.json`，同配置再次运行会覆盖当前结果。日志、导入缓存和 JSON 均不上传 Git。

## 优化前基线结果

11 人 / 5 敌人和 33 人 / 15 敌人的 3 倍速结果：

| 场景 | 敌人出现：平均 / P95 帧时 | 持续战斗：平均 / P95 帧时 | 暂停迷雾刷新：平均 / P95 帧时 |
| --- | --- | --- | --- |
| 11 人 / 5 敌人 | 13.81 / 26.82 ms | 13.34 / 20.63 ms | 13.34 / 16.97 ms |
| 33 人 / 15 敌人 | 24.72 / 60.75 ms | 22.22 / 57.62 ms | 13.34 / 19.80 ms |

11 人测试中，无敌人且居民工作阶段单次迷雾刷新平均 21.13 ms；生成视野遮罩约 10 ms，对象显隐约 6.97 ms，树木收集与树冠修补也有开销。居民避难后，持续战斗的迷雾刷新平均 11.05 ms，其中对象显隐平均 8.79 ms，视野源未移动时不再生成遮罩。

注意：生成遮罩、遮挡角度等分项的 `count` 可能小于总刷新次数；其均值只覆盖实际执行的调用。统计分项与总量时应核对调用次数，不能把不同分母的均值直接相加。

66 人 / 30 敌人的完整倍速对照：

| 阶段 | 1 倍速平均 / P95 帧时 | 3 倍速平均 / P95 帧时 | 3 倍速平均帧率 |
| --- | --- | --- | --- |
| 无敌人、居民工作/待命 | 83.61 / 141.47 ms | 60.80 / 140.83 ms | 16.4 FPS |
| 敌人出现与避难 | 158.14 / 216.97 ms | 173.08 / 225.73 ms | 5.8 FPS |
| 持续战斗 | 158.14 / 221.45 ms | 155.81 / 212.32 ms | 6.4 FPS |
| 暂停迷雾刷新 | 36.18 / 45.71 ms | 35.30 / 43.69 ms | 28.3 FPS |
| 再暂停单位 AI | 13.24 / 14.88 ms | 13.31 / 13.81 ms | 75.1 FPS |

3 倍速敌人出现阶段，360 帧中 355 帧超过 142.857 ms；持续战斗阶段 196/360 帧超过该值，因此是持续低帧，而非单次尖峰。两阶段平均每渲染帧分别执行 8.00、7.97 次居民物理更新；暂停迷雾刷新后降至 2.12 次。1 倍速敌人出现与持续战斗阶段同样达到每帧 8 次更新，慢帧数量分别为 355/360、359/360。

3 倍速敌人出现阶段，单次迷雾总刷新平均 61.34 ms：生成视野遮罩在实际执行时平均 46.03 ms，其中遮挡角度 12.93 ms、平滑 10.52 ms；像素合并按全部刷新计平均 22.19 ms。对象显隐平均 11.49 ms，树木数据收集 1.71 ms，树冠修补约 1.97 ms。其余数据整理、复制与纹理提交约 0.98 ms。持续战斗阶段总刷新平均约 51.47 ms。

## 结论与后续优先级

1. **迷雾是已确认的重要 CPU 开销。** 33 人和 66 人阶段暂停刷新都有明显改善；主要开销随可移动视野源数量增加，集中在 GDScript 的遮挡角度、平滑与像素合并。11 人避难后的固定视野场景则主要耗在对象显隐，优化时不能只处理绘图。
2. **单位逻辑也是高人口瓶颈。** 66 人时暂停迷雾后仍只有约 28 FPS，继续暂停单位 AI 才恢复到约 75 FPS。3 倍速持续战斗阶段，居民物理脚本平均约 56.7 ms/渲染帧，敌人物理脚本约 9.4 ms，敌人每帧选敌约 9.1 ms；这些是补帧后累计到一渲染帧内的成本，不是单次物理更新成本。
3. **长帧与物理补帧工作叠加。** 低帧阶段每个渲染帧执行接近 8 次物理更新；暂停迷雾后帧时与物理更新次数同时下降。这支持优先降低刷新尖峰，再优化频繁选敌与移动/避让查询。仅降低倍速不能解决此人为拥挤场景的问题。
4. **没有复现用户原来的 11 人 / 5 敌人第 19 分钟现场。** 此次在 66 人 / 30 敌人的密集布局复现了相同量级的持续低帧，证明负载机制存在，不能宣称找到了原现场的唯一原因。真实关卡建筑数量、道路、任务和资源清理状态仍可能改变结果。

基线建议先优化视觉遮罩的 CPU 计算和静态对象显隐重复更新，并继续保持树木遮挡、树冠显示和游戏可见性判定的等价回归；随后检查单位选敌与拥挤避让的查询频率。基线阶段只新增诊断测试与报告，没有调整刷新精度、刷新频率、物理补帧上限或正式玩法。

四份正式结果（11/33/66 人 3 倍速和 66 人 1 倍速）均完成五个阶段，居民、敌人数量保持预期，退出码为 0，日志没有 `SCRIPT ERROR` 或 `ERROR:`。测试初期曾因据点血量接口与训练后血量重设导致测试脚本失败，修正后重跑；早期失败运行不计入上述结果。

## CPU 缓存优化与复测

本次只修改迷雾 CPU 刷新路径：

- 新增、删除节点时只失效该节点及祖先的显隐子节点缓存，避免战斗特效导致全场对象重新扫描。
- 资源与植被的显隐结果没变化时，跳过重复写入子网格显隐和碰撞拾取状态；建筑、单位等动态对象继续更新。
- 缓存像素世界坐标和遮挡射线方向，减少重复计算；平滑滑动窗口以递增索引代替重复环绕取模。
- 树木遮挡没变时，复用上一轮相同位置、相同实际视野半径的遮挡角度和平滑结果。只保留当前与上一刷新数据，单位移动、昼夜半径改变或树木遮挡改变都会重算对应数据。
- 用原生字节数组扫描跳过每行连续完全照亮的像素，避免这些重叠区逐像素执行 GDScript。没有待合并像素时直接结束该行。

保留 256×256 遮罩、720 条角度射线、原来的树木遮挡与边缘平滑、每 0.1 真实秒刷新；没有降低精度、延迟单位反应或改变物理补帧上限。

正式复测使用最终版逐个启动游戏进程，期间没有并行运行其它测试。优化前 JSON 留在本机 `.godot/fog_optimization_before/`，优化后 JSON 为默认输出路径；对应日志以 `_optimized.log` 结尾。中间方案的单次测量不计入以下最终结果。

| 场景与阶段 | 优化前平均 / P95 帧时 | 优化后平均 / P95 帧时 | 平均帧率前 → 后 |
| --- | --- | --- | --- |
| 11 人 / 5 敌人，3 倍速持续战斗 | 13.34 / 20.63 ms | 13.34 / 17.61 ms | 75.0 → 75.0 FPS |
| 33 人 / 15 敌人，3 倍速持续战斗 | 22.22 / 57.62 ms | 15.01 / 35.43 ms | 45.0 → 66.6 FPS |
| 66 人 / 30 敌人，3 倍速敌人出现 | 173.08 / 225.73 ms | 140.97 / 172.04 ms | 5.8 → 7.1 FPS |
| 66 人 / 30 敌人，3 倍速持续战斗 | 155.81 / 212.32 ms | 135.81 / 179.74 ms | 6.4 → 7.4 FPS |
| 66 人 / 30 敌人，1 倍速持续战斗 | 158.14 / 221.45 ms | 140.22 / 172.45 ms | 6.3 → 7.1 FPS |

66 人 3 倍速敌人出现阶段，单次迷雾总刷新从 61.34 降到 32.61 ms；持续战斗从 51.47 降到 29.55 ms。敌人出现阶段，遮挡角度均值从 12.93 降到 2.68 ms，平滑从 10.52 降到 2.59 ms，对象显隐从 11.49 降到 6.35 ms。像素合并按全部刷新计从 22.19 降到 16.72 ms。分项仍需核对各自调用次数。

**优化了迷雾成本，但没有解决 66 人重压低帧。** 最终 3 倍速敌人出现与持续战斗阶段仍平均执行 7.95、7.60 次物理更新/渲染帧，超过 142.857 ms 的帧分别为 113/360、109/360。居民物理脚本仍约 63 ms/渲染帧，敌人物理脚本约 10 ms，选敌约 9.5 ms。暂停迷雾后约 24 FPS，再暂停单位 AI 才恢复约 75 FPS。正式玩法中需要继续检查单位逻辑与拥挤避让，不能把降低迷雾成本直接解释为游戏帧率同比提高。

不同运行中的 AI、采集和战斗状态会演进，不能将数毫秒波动当作严格确定收益；这里确认的是迷雾刷新成本降低，以及 33 人场景整体帧时明显改善。用户原始 11 人 / 5 敌人、第 19 分钟掉帧现场仍未复现。

四份最终优化结果均完成五阶段，人口、敌人数断言符合预期，进程退出码为 0，日志没有 `SCRIPT ERROR` 或 `ERROR:`。以下回归也全部退出 0、无脚本错误：

- `fog_pixel_equivalence_test.gd`：3 种视野倍率、连续刷新、重叠视野与树遮挡，三张图逐字节一致。
- `fog_smoothing_equivalence_test.gd`：平滑算法对照。
- `fog_visibility_cache_test.gd`：三张图对照完整旧算法；验证单个居民移动只重算自身角度和平滑，以及昼夜、砍树、建筑变化、地图尺寸变化、地图外视野源、全图照亮后的空行扫描。
- `fog_object_lifecycle_test.gd`：无关节点不清全场缓存，子网格增删正确失效，删除对象不保留失效缓存，动态建筑显隐仍更新。
- `fog_tree_visual_test.gd`、`fog_death_render_test.gd`、`fog_building_placement_test.gd`：实际 Forward+ 渲染中的树林、火把、居民显隐与死亡、未照亮区域建筑放置。

已查看真实树林截图 `.godot/fog_tree_preview.png`；该图在启动阶段拍摄，HUD 帧率数值不能当作持续帧率测量。上述性能表使用压力脚本的真实帧间隔。

## 单位与其它开销细分排查

继续在测试子类中计时，不修改正式单位行为。增加居民搜敌、避难流程、战斗流程、生活需求、每帧回血脚本、门口查询、道路路径更新、双方移动避让、敌人墙体射线、主场景与 HUD 刷新，以及函数调用次数、绘制调用、绘制图元、节点数和孤立节点数。另增加暂停迷雾后临时绕过避让的诊断阶段；角色仍使用实体碰撞移动。这个阶段改变了移动行为，只用于定位，不能作为游戏优化方案。

33 人与 66 人的完整细分测试均完成六阶段、退出 0、没有脚本错误。额外包装计时有开销，不能直接将该轮总帧率当作前一节正式优化版的性能回归。所有 CPU 数字以真实渲染帧为分母，包含该帧内的多次物理更新。

66 居民 / 30 敌人、3 倍速持续战斗的最终细分结果：

| 项目 | 平均 CPU 时间 / 渲染帧 | 说明 |
| --- | --- | --- |
| 居民搜敌 | 32.98 ms | 平均 399 次调用，每次遍历敌人组；是居民物理脚本的子项 |
| 双方移动避让 | 17.95 ms | 平均 255 次调用；包含形状查询、导航投影和试移动；属于双方移动的子项 |
| 敌人每帧选敌 | 9.26 ms | 30 个敌人每渲染帧扫描居民和敌人，另有目标合法性与优先级判断 |
| 居民移动总流程 | 24.34 ms | 包含居民避让、路径获取、朝向和实体移动 |
| 敌人移动总流程 | 6.93 ms | 包含敌人避让、路径获取、朝向和实体移动 |

表中父项与子项重叠，不能相加。居民物理脚本总计 71.64 ms，敌人物理脚本总计 13.23 ms。敌人墙体射线在该无城墙压力布局中没有持续开销，不能据此判断大量城墙时的成本。

重复运行的66人持续战斗中，居民搜敌都约 33 ms，双方避让约 15–18 ms，敌人选敌约 9.3–9.5 ms。最终持续战斗阶段每渲染帧平均 7.97 次物理更新，重复搜索因补帧而放大。暂停迷雾阶段 65.94 ms/帧，临时绕过避让后 40.43 ms/帧，再暂停单位 AI 后 13.25 ms/帧。前一轮相同对照为 49.65 → 37.18 → 13.24 ms/帧；AI 与拥挤状态有波动，不能把两阶段差值当成避让函数精确耗时，但两轮都确认了避让成本。

该场景持续战斗平均约 1197 次绘制调用、175 万个绘制图元、12793 个节点。数量说明渲染批次仍有优化空间，但暂停单位 AI 后保留场景渲染仍可约 75 FPS，因此当前严重低帧首先应处理 CPU 查询。没有独立测量 GPU 毫秒数，不能宣称 GPU 在所有场景都没有瓶颈。短测试中节点数稳定、孤立节点为 0；这不能替代第 19 分钟现场的长期资源泄漏检查。当前渲染后端的碰撞对数监视器一直返回 0，不能将其解释为没有碰撞成本。

**下一步优先级：**

1. 减少每个居民对完整敌人组的重复扫描：共享有效敌人数据、做空间范围筛选，并保持死亡、隐藏、阵营变化的及时失效。
2. 优化敌人重复选敌，保留合法目标验证和优先级；避免每渲染帧重新对所有对象执行相同判断。
3. 深入拆分避让内部的形状查询、导航最近点和试移动，针对拥挤停滞做优化，保留避障行为。
4. 处理避难位不足时的据点入口拥堵。两轮测试均有 43 名居民停留在 `RETREAT_TO_BASE`、10 名 `SHELTERED`。代码无可用避难位时回退到据点交互位置，持续触发移动与避让；下面的容量对照确认了这组布局的拥堵会放大负载。

以上首先是诊断结论，不是新增人数上限；本轮没有修改正式游戏脚本。

### 避难容量对照

使用相同的 66 居民 / 30 敌人、3 倍速布局，只在测试进程内将已有住宅节点的 `housing_capacity` 临时设为 66。建筑数量、位置与网格不变，没有修改住宅资源或正式游戏代码。此操作允许更多居民进入室内，会减少室外可见单位和活跃移动负载，不能用来证明 96 个单位同时在野外战斗也能达到相同帧率。

| 持续战斗指标 | 原容量 | 测试扩大容量 |
| --- | --- | --- |
| 避难状态 | 43 名仍前往避难、10 名室内 | 53 名室内、没有居民继续前往避难 |
| 平均帧时 / 帧率 | 144.67 ms / 6.9 FPS | 37.60 ms / 26.6 FPS |
| 居民搜敌 | 32.98 ms | 10.11 ms |
| 双方移动避让 | 17.95 ms | 0.093 ms |

扩大容量后暂停迷雾为 22.39 ms/帧，再绕过避让为 21.83 ms/帧，再暂停单位 AI 为 13.23 ms/帧。这说明有足够避难位时，持续避让成本基本消失；仍需优化室内居民的敌情检测、敌人选敌和迷雾。`SHELTERED` 分支目前仍在每次物理更新执行 `_find_nearest_hostile()`。

复测命令：

```powershell
godot --path . --script res://Tests/fog_raid_stress_test.gd -- --population=66 --speed=3 --shelter-capacity=66
```

结果为 `.godot/unit_profile_stress_66_3x_shelter_66.json`，六阶段均完成，人数保持预期，退出 0，无脚本错误。有限时段对照确认了当前压力布局的容量因素，仍不能替代用户原始存档验证。
