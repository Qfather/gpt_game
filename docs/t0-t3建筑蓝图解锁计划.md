## 1. 目标（一句话）

**复用现有 `addons/resource_editor` 的“建筑”插件，做一个可在 Godot 编辑器中添加、删除、修改和校验的 T0～T3 建筑升级树；将兵种训练改为同一套可配置逻辑。** 先以 `T0 民兵营 → T1 剑士营 / 弓箭手营` 跑通完整实际游戏流程。以后扩展炮兵营、重炮营以及其他兵营分支时，主要在编辑器中配置，不再复制整个训练脚本。

### 1.1 必须达到

- 建筑具有可编辑的 **T0/T1/T2/T3 等级**、上一级建筑、升级成本与升级时间；允许**一对多分支**。
- 建筑插件内能**增删建筑定义、设置等级、选择父级、设置分支**，直观查看进化树；能检测缺失引用、循环、错误级别等配置错误。
- 建筑的**可训练单位列表**在插件中增删；每个训练条目可以设置单位、时间、资源消耗，建筑配置训练槽位；编辑完成后直接影响运行时。
- **T0 默认解锁**；T1～T3 通过**本局蓝图解锁**相应升级权限，解锁后同类建筑可重复升级，不是蓝图仅允许造一座。
- **T1～T3 军事建筑不在普通建造菜单直接出现**，通过低级兵营原地升级（除非某建筑明确被配置为允许直接建造）；用户可独立选择每座建筑的分支。
- 军事训练复用目前的居民走路、进门、排队、消耗资源、训练进度、完成转职、取消退款、死亡和任务释放机制，不能另外造一个不兼容的任务系统。
- 保留当前**木制城墙/城门/塔楼 → 石制**升级功能、普通建筑建造、拆除、狩猎、驻军、暂停操作等已有行为。
- 新增 **T0 民兵营 + 民兵单位**（可先使用占位模型）；在不解锁高级兵营时能训练民兵进行基础防御。

### 1.2 本次先不做

- **不做完整 Roguelite 三选一卡牌界面**、刷新概率、局外成长、永久科技树和存档版本迁移。只做可调用的“本局蓝图解锁状态”及一个开发测试入口，供后续抽卡 UI 接入。
- **不做炮兵/火炮的新战斗 AI、弹道、范围伤害和正式模型**；仅使未来可以在编辑器中创建 T2/T3 建筑分支与训练配置。特殊新单位的独有行为仍可需要专门代码。
- 不增加木板、铁矿、石砖等经济资源，不顺带修改移民三阶段食物规则、敌袭数值或其他玩法。
- 不修改地图生成器 `addons/MapGenerate` 子模块，不进行无关重构。

## 3. 玩法规则与数据约束

### 3.1 T0～T3 的含义

- **T0：基础建筑**，进入关卡自动拥有建造权限；例如伐木场、采石场、农舍、民兵营等。既有道路、防线等非进化型建筑按旧规则运行，不要强制改为兵营升级树。
- **T1/T2/T3：进阶建筑**，默认需要本局对应蓝图才允许升级；等级用于限制升级顺序，不能只改变菜单显示。
- **等级不等于一次性科技全解锁**。抽到“剑士营蓝图”只解锁该建筑分支；不自动解锁其 T2、T3 子节点。
- **建筑蓝图解锁后可重复使用**：若已有 3 座民兵营，可以独立将其中任意数量升级为已解锁的分支（分别消耗成本）。
- 一个建筑的**直接父级先只支持 1 个**，但父级可拥有无限多个子分支。例：民兵营的子级可以同时有剑士营、弓箭营、炮兵营。未来确需“多父级合成”时再扩展，避免当前复杂化。
- 常规进化仅允许 **Tn → T(n+1)**，不能跨级、降级或改走平级分支。升级默认**不可逆**；以后若需要洗点单独设计。
- **同一种建筑的多个实例可以进化为不同分支**；升级改变某一建筑实例，不会将地图上所有该类建筑自动升级。
- 蓝图系统是**进化权限**，不是直接生成免费建筑。升级仍受资源、建筑状态和施工限制。

### 3.2 推荐首版升级树

```text
T0 民兵营（默认可建，训练民兵）
├── T1 剑士营（蓝图解锁，训练民兵 + 剑士）
│   ├── T2 重装兵营（仅允许配置，暂不做单位逻辑）
│   │   └── T3 精锐兵营（仅允许配置）
│   └── T2 其他近战分支（预留）
├── T1 弓箭营（蓝图解锁，训练民兵 + 弓箭手）
│   └── T2 长弓营（仅允许配置）
└── T1 炮兵营（仅允许配置，不实现炮兵单位）
    └── T2 重炮营（仅允许配置）
        └── T3 特种火炮营（仅允许配置）
```

**仅须在这次真正生成并调通**：`T0 民兵营`、`T1 剑士营`、`T1 弓箭营`。T2/T3 的新增、删除、参数校验和树预览必须可用，但不用制造无素材的虚假单位。编辑器可创建未接场景的**草稿节点**，草稿不得进入游戏运行时可选蓝图池；不能让空场景或不存在的兵种造成崩溃。

### 3.3 升级与训练关系

- 民兵营训练 `militia`。
- 剑士营默认训练 `militia` + `swordsman`；弓箭营默认训练 `militia` + `archer`。**同一座建筑可配置多个训练项**，在游戏详情面板分别显示按钮。
- **升级后保留民兵训练能力**是这次首版的配置结果，而非写死在训练代码中；未来可以从任意高级兵营删掉民兵训练项。
- 训练中的普通居民不会因为建筑被替换而丢失。首版采用简单安全策略：**有正在训练的居民、待认领训练任务、已预定训练槽位时，禁止启动升级**，显示“请先完成或取消训练”。
- 完工升级后，已训练出来的单位仍存活、职责不变；不会自动把民兵升成剑士或弓箭手。

## 4. 数据设计（建议实现，允许在不破坏功能的前提下微调命名）

### 4.1 扩展 `BuildingData`

建议在现有 `BuildingData` 增加以下**可序列化的导出字段**，继续存入 `data/buildings/*.tres`：

| 字段（建议名） | 类型 | 说明 |
|---|---|---|
| `tier` | `int` (0～3) | 建筑科技等级，编辑器下拉显示 T0/T1/T2/T3 |
| `upgrade_from_id` | `StringName` | 直接父建筑的稳定 ID；T0 为空 |
| `enable_evolution` | `bool` | 是否参与建筑升级树；道路、防线等旧特殊系统可保持关闭 |
| `requires_blueprint` | `bool` | T1～T3 默认 `true`；T0 默认 `false` |
| `allow_direct_build` | `bool` | T0 默认 `true`；有父级的进化建筑默认 `false` |
| `upgrade_cost` | `Dictionary[StringName,float]` | **此次进化单独付出的成本**（非总造价）；不要让空配方意味着免费升级 |
| `upgrade_time` | `float` | 此次原地升级需要的施工秒数 |
| `training_slots` | `int` | 这座建筑的总训练并发槽位（放在通用建筑数据中） |
| `training_recipes` | `Array[TrainingRecipe]` | 可添加/删除/排序的训练配方资源数组 |

其中 `TrainingRecipe` 建议是一个新的 `Resource` 类，至少有：

| 字段 | 说明 |
|---|---|
| `unit_id: StringName` | 指向 `data/units` 注册的现有 `UnitData.id`；不要用界面中文名或枚举序号作为跨资源引用 |
| `cost: Dictionary[StringName,float]` | 此兵种单次训练的真实资源成本 |
| `time_seconds: float` | 此兵种训练时间 |
| `display_order: int` | 详情面板中训练选项显示顺序 |
| `enabled: bool` | 允许暂时禁用该训练项而不删除配置 |

可用现有单位数据与角色映射做首版通用训练。**以后不同兵种若有特殊技能、独立炮车场景或多人口占用，仍需要针对对应单位行为实现代码；编辑器负责数据和训练流程，不承诺凭空生成新战斗 AI。**

配置与运行职责分离：`BuildingData`/`TrainingRecipe` 不承载任务执行状态；训练工人、训练预订、计时与材料扣费应留在运行时实例/现有任务系统。

### 4.2 唯一稳定 ID 与升级索引

- `id` 不得重复，场景、蓝图、存档接口都用稳定 ID 引用，**不要依赖文件名、数组索引、展示名**。
- 构建一个小型**建筑数据索引/查询服务**（可借鉴现有扫描逻辑，避免每帧扫描目录）：`get_building(id)`、`get_children(parent_id)`、`get_unlockable_upgrades(current_id, unlocked_ids)`、`validate_tree()`。
- 加载时建立索引；编辑器手动刷新或资源改变时重建。不要把目录全量扫描或数据深拷贝放进单位 `_process()`。
- 校验：空 ID、重复 ID、无效 tier、父节点缺失、父子级不连续、自己指向自己、循环引用、场景/单位缺失、资源 ID 无效、成本为负、训练时间 ≤0、槽位为 0、重复训练条目。
- 对已有普通建筑自动设置向后兼容默认值，避免一次新增字段导致旧 `.tres` 失效。
- 资源文件不允许直接删除已被其他建筑引用的父节点；编辑器至少提供引用列表、二次确认并阻止误删。**删除配置不等于自动删除正在运行的建筑实例。**

### 4.3 本局蓝图解锁状态（只做接口，不做完整抽卡）

提供一个轻量运行时服务（命名可按工程风格）：

```gdscript
unlock_building_blueprint(building_id: StringName) -> bool
is_building_blueprint_unlocked(building_id: StringName) -> bool
get_available_upgrade_targets(source_building_id: StringName) -> Array[BuildingData]
```

- 每局新建时初始化 T0 可建权限；T1～T3 初始锁定。
- 接口要能被未来的“三选一蓝图面板”直接调用；信号通知 HUD/建筑详情刷新，而不是每帧反复扫描。
- 开发模式加临时调试入口：手动解锁剑士营/弓箭营，并能看到按钮由锁定变为可升级，用于验证。
- 为将来关卡初始化、随机蓝图池留出清晰接口；**本次不实现掉率、保底和随机抽牌逻辑**。

## 5. 编辑器插件 UI 需求

在现有底部“建筑”插件里扩展，保持已有“通用建筑属性 / 建筑专属参数 / 资源仓储”等功能；不要新建一个与当前建筑数据不同步的独立插件。

### 5.1 建筑列表与增删

- 建筑列表可按**等级 T0～T3**筛选，也保留原有“生产/军事/战略/道路/加工”分类。
- 列表显示：`[T1] 剑士营 | 父级：民兵营 | 蓝图锁定`，并支持按名称检索（若实现成本低）。

- `删除建筑`：显示引用和确认；检查其子分支、场景引用及其他已知配置引用；存在依赖则阻止或要求先手动解除。
- `保存 / 刷新` 要正确处理当前项目已有自动保存逻辑。禁止刷新时丢失未保存配置或场景专属参数。

### 5.2 新增“进化树”页签

**可直接操作的最简 UI 即可，先不追求华丽的图形连线。**

- 左侧树状列表：显示民兵营下的剑士/弓箭营分支，T2/T3 继续缩进。
- 右侧所选节点参数：等级、父建筑、是否需要蓝图、是否允许直接建造、升级成本、时间、场景预览。
- 操作按钮：`新增子分支`、`复制分支`、`删除分支`、`重新指定父级`、`校验整个升级树`。
- 点击一个节点可跳转到该建筑既有通用属性编辑页面。
- 不允许选成自己的祖先、T0 指向 T1、T1 直接指向 T3 等非法操作；保存时显示明确错误而非默默吞掉。
- 在编辑器中修改父级或等级后树结构立即更新，并正确持久化到 `.tres`，重启编辑器后仍然一致。

### 5.3 新增“训练配置”页签/分组

- 训练建筑可选择多个单位配方：`+ 添加训练项`、`删除`、`上移/下移`。
- 每个训练项显示：**单位**（从已有单位数据库下拉选择，而不是手打枚举索引）、**成本**（从资源数据库选择）、**训练时间**、启用与否。

- 预览游戏内实际会显示的按钮名称、成本和训练时间，帮助后期调数值。

## 6. 运行时升级：接入原有施工系统

**不要用 `queue_free(old)` + `instantiate(new)` 的裸替换绕开工地、网格、动画、费用、导航和单位引用。** 优先复用 `BuildingBase`、`ConstructionSite` 当前的原地升级通路，扩展为可指定目标建筑 ID；旧石制防线升级要继续可用。

### 6.1 升级流程

1. 点击某座已完工民兵营 → 显示当前 T 等级、训练条目和所有**直接子级**升级方案（锁定方案可显示灰色并写清原因）。
2. 选择已解锁的剑士营/弓箭营 → 检查建筑存活、无待拆除/其他升级、没有正在/排队的训练、目标级别合法、目标尺寸/朝向/入口安全、没有非法覆盖。
3. 点击升级 → 以配置好的升级成本和时间创建原地工地；沿用现有工人运料、施工、取消、材料回滚和暂停规则。
4. 完工 → 把当前**这座**民兵营替换为对应 T1 场景，保留世界位置、四向旋转、镜像、占地登记、可合法继承的库存与驻守/工作关系；更新选中建筑和 HUD；完成导航/占地刷新。
5. 另一座民兵营不受影响，可选择相同或不同分支。

**首版限制**：民兵营与剑士/弓箭营应采用相同网格占地（建议复用目前剑士/弓箭营的 3×3）和兼容的入口相对位置。若目标占地、门位置不兼容，编辑器/运行时给出错误并阻止升级；不为了“升级成功”而允许瞬移穿墙。

### 6.2 升级中的生命与状态

- 受损建筑升级后的 HP 保留合理**生命百分比**，不因升级凭空满血（具体方案遵循现有建筑耐久约定）。
- 已有训练完成的民兵、剑士、弓箭手不自动变更职业。
- 升级不能覆盖正在训练的人员；升级前要求队列和入口预约为空是本次的最简解法。
- 对已有驻军和补粮缓存，若源与目标都支持同一功能，则安全迁移有效引用；不适用的功能按已有解除/返回机制处理，不能留下指向已销毁建筑的居民/任务。
- 玩家取消升级时保留原建筑，工地与资源退回遵循项目现有规则。
- 同时选中多个建筑升级：旧防线批量升级行为不变；军事分支优先保证**单栋**安全选择，批量同分支以后再考虑。

## 7. 公共训练系统：真正按训练项工作

### 7.1 保留现有“居民训练转职”完整链路

- 玩家选择建筑详情中的某个训练项，如“训练民兵”“训练剑士”。
- 校验此建筑是否配置并启用该配方、槽位是否足够、资源是否足够、居民是否合法（避免把已经是士兵的人再次当普通居民招募）。
- **创建通用训练任务**，任务携带 `unit_id`、**配方快照**（成本、所需时间）与建筑引用；原有任务分配逻辑安排合格的空闲居民。
- 居民按**真实可达的建筑正面入口**前往，排队入屋，训练时正确隐藏/显示，计时受游戏速度与暂停影响。
- 完成时按指定 `unit_id` 应用单位数据和战斗职责、正确结束任务并离开建筑。
- 取消、死亡、建筑拆除、任务重派时：避免重复扣费/退款、悬空训练槽、幽灵训练者或角色不可见。

### 7.2 不再使用“固定剑士训练任务”作为新设计的唯一身份

- 现有 `GameTask.TaskType.TRAIN_SWORDSMAN`、`SwordsmanCamp.training_role`、`BuildingData.training_cost`、`resource_building_panel.gd` 的单训练按钮为迁移重点。
- 推荐提供通用 `TRAIN_UNIT` 任务（或保留旧枚举兼容但逻辑已彻底通用），具体训练哪种单位只由任务数据决定。旧测试若依赖旧枚举值应提供兼容迁移，不可直接无说明删除。
- 新增公用 `TrainingFacility` 行为/基类并由民兵营、剑士营、弓箭营复用；旧场景可先继续使用现有脚本路径作为薄封装，避免大量场景引用失效。
- 训练配方每次申请时进行一次资源查询/预留；**不要每帧全图扫描仓库或居民**。
- 训练成本扣款与退款必须使用申请时的**实际费用快照**，不能中途修改建筑数据导致退错资源。
- UI 展示每个兵种的训练状态；如果槽位是整栋建筑共享，则不能通过同时点击不同按钮绕过总槽位上限。

### 7.3 民兵的具体首版要求

- 新增 `militia` 对应 `UnitData`、视觉占位及战斗角色。
- **民兵是主动承担基本作战职责的弱兵种，不是普通居民有攻击力后自动参战**；继续保持居民避险、猎人自卫的既有职责规则。
- 民兵用现有居民训练流程转职；可以低成本、快速训练，初期能抵御小规模袭扰；本次**不需要确定最终数值**，先提供编辑器可调字段并用临时测试值。
- 如现有驻军/巡逻只接受剑士和弓箭手，要明确民兵哪些能力可用，哪些暂不可用；不要为实现民兵偷偷改变箭塔“只有有效弓箭手驻守”的判定。
- T0 民兵营加入普通建造菜单；T1 兵营从普通建造列表隐藏，仅在民兵营的进化分支展示。

### 7.4 预留未来炮兵，但不夸大本次能力

- 编辑器能够配置“炮兵营 → 重炮营”的 T 级结构；训练条目可指向未来定义的单位数据。
- 目前所有已实现训练仍采用**居民转职单位**模式。未来炮车等独立实体可以扩展“训练产出类型（居民转职/生成单位）”，**本次先不实现空有名字但无法工作的炮兵生产模式**。

## 8. 开发顺序：分阶段实现与检查

> 各阶段按顺序完成；修改源码可一次性交付，但**不得只做可视化配置然后声称玩法已完成**。

### 阶段 A：数据与编辑器

1. `BuildingData` 增加 T 级、父级、成本、时间、训练配方字段。
2. `TrainingRecipe` 资源类及建筑索引/树校验工具。
3. 现有建筑编辑器支持新建、安全删除、T0～T3 过滤、树增删和训练列表编辑。
4. 旧建筑数据能正常加载；T2/T3 草稿能够创建、删掉、保存、重开仍正确。

**验收 A**：编辑器从 0 创建一个 T2 分支、设置父级、修改升级成本和 2 个训练配方、保存重启后字段不丢；故意制造无效父级/循环时显示错误并禁止启用。

### 阶段 B：通用训练与民兵

1. 将现有剑士/弓箭手训练流程改为数据驱动通用训练。
2. 新增民兵数据/场景、T0 民兵营场景/建筑数据。
3. 建筑详情显示多项训练按钮与独立配方成本；共享训练槽位。
4. 正常训练/被打断/取消/拆除/暂停的逻辑完整回归。

**验收 B**：民兵营训练民兵；既有剑士营和弓箭营仍能正常训练原兵种；剑士营配置两种训练项时可分别训练民兵与剑士；无重复扣费退款或居民卡死。

### 阶段 C：军事建筑进化与本局解锁

1. 新增本局蓝图解锁状态及调试入口。
2. 民兵营显示锁定的剑士营/弓箭营升级分支；解锁后可各自独立选择。
3. 利用原有工地完成原地升级；正确处理选中对象、导航、施工成本和状态迁移。
4. HUD 过滤不可直接建造的 T1～T3；既有木墙升级完全不变。

**验收 C**：建造两座民兵营，手动解锁剑士营/弓箭营；将一座升级为剑士营，另一座升级为弓箭营；正常训练，各自独立。取消升级后原建筑还在，材料规则正确；锁定的蓝图不能通过 HUD/代码入口绕过。

### 阶段 D：专项回归、性能与交付

1. 运行下节测试，并手动执行有画面的进门/训练/升级流程。
2. 检查 1×、3×、暂停时的训练与升级时长、资源扣费。
3. 记录变更、测试结果及未解决问题，不顺带平衡全部游戏数值。

## 10. 客户端实现约束与交付标准

1. **先盘点当前相关代码，最小化修改面**。严格遵循 `AGENTS.md`；任务涉及移动和训练必须读 `docs/移动与导航约束.md`。不要改动 `addons/MapGenerate` 子模块。
2. 以**配置驱动**替代建筑名称/ID 的分支判断，但不为了这次任务全面推倒重写 `villager.gd`、`task_manager.gd` 或城墙升级。
3. 新增功能应与现有自动保存、资源扫描、Godot `.tres` / `.tscn` 编辑兼容，禁用无效草稿资源进入运行时。
4. **不能在高频逻辑打印大量调试日志、重复全局扫描或逐帧重建建筑索引**，遵守当前项目性能优化原则。
5. 有 `await` 的入屋、训练、升级、取消回调必须在恢复时复核对象有效性与当前任务 ID，避免陈旧任务继续操作。
6. 暂停时玩家点击解锁、选择分支等**命令可以即时生效**，但施工/训练的游戏进度保持暂停；3 倍速按游戏时间正常推进。
7. 升级、拆除、训练成本和退款不能出现无中生有或重复消耗。
8. 更新 `README.md` 的当前能力、`docs/开发日志.md` 的实际变更与测试、必要的插件使用说明；未完成的炮兵等只列在规划，不写成已可用。
9. **不要擅自提交、推送、覆盖仓库或清理用户资产。**

### 交付时请客户端明确回复

- **改动文件清单**及新增资源/场景；各自作用。
- **编辑器使用方法**：如何创建 T0～T3 建筑、添加分支、配置训练项、保存、删除与查看错误。
- **游戏运行方法**：如何建民兵营、测试训练、调试解锁剑士/弓箭营、原地升级。
- **测试结果**：通过、失败、因环境未运行的测试逐项说明；记录关键日志或截图要点。
- **待办/限制**：例如 T2/T3 只是编辑器草稿、炮兵战斗逻辑未做、完整蓝图三选一卡牌未做。

## 11. 最终验收场景（全部走通才算完成）

1. 打开现有工程，“建筑”编辑器有 T0～T3 进化树和训练配置入口。
2. 在插件中创建/编辑/删除测试建筑分支并保存成功，编辑器重启仍正确；无效引用可见报错。
3. 新局里 T0 民兵营可建，T1 剑士营、弓箭营**不能直接建造**；未解锁升级显示锁定。
4. 民兵营消耗指定资源、指派普通居民，居民**实际走进门**，完成训练后成为能战斗的民兵。
5. 通过开发测试入口解锁两张 T1 蓝图，建两座民兵营：分别升级为剑士营、弓箭营；升级工程确实消耗资源和施工时间。
6. 两种高级兵营都保留可配置的民兵训练项，同时能分别训练剑士、弓箭手；训练队列、取消和拆除不破坏居民/任务/资源。
7. 木墙到石墙的既有升级、其他基础建筑及原有军事测试仍能正常运行。

**用户确认的设计决定：军事升级树是 Roguelite 进化塔式结构——民兵营作为 T0 起点，T1～T3 随机蓝图解锁分支，升级的是一座具体建筑，训练逻辑共用一套。**
