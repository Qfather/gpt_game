# 《时间裂缝》项目知识库整理执行计划

> 执行对象：可以访问本地 Godot 工程的 GPT 客户端 / 编程助手  
> 任务性质：**只整理信息与文档，不开发新功能、不重构代码**  
> 目标：将散落在工程文件、已有 Markdown、TODO、注释和参考资料中的内容整理为一个便于长期维护的项目知识库。

## 0. 最高优先级约束

1. **先盘点、后写入**。先了解项目现状和文档分布，不要按想象补齐功能。
2. **禁止修改游戏逻辑**。不得编辑 `.gd`、`.tscn`、`.tres`、`.godot`、模型、贴图、插件或其他运行资源；只允许新建/修改本计划指定的知识库 Markdown 文件。确有必要改代码时，单独列为建议，等待用户后续决定。
3. **保护现有资料**。不删除、不移动、不覆盖原文档；先建立新知识库并引用旧资料。对重复文件先记录关系，不自动清理。
4. **区分事实和计划**：工程中可验证的功能标记为“已实现（待测试）”；确认有测试或实际验证证据后才能标为“已验证”；只有聊天/规划中出现的功能标记为“计划中/待核实”。
5. **不要把推测写成事实**。无法确认的信息写“待确认”，附上需要检查的文件或问题。
6. **减少上下文消耗**。按目录分批读取工程；忽略 `.git/`、`.godot/`、缓存、导入产物及大型二进制资源，不将完整代码复制进文档。
7. **每个重要结论注明来源**。优先使用仓库相对路径、具体脚本/场景/现有文档路径；不必逐行引用，但应能回查。
8. 若目标文件已存在，先读取并合并；避免覆盖用户手工修改。执行前确认当前 Git 工作区状态，并尊重已有未提交变更。

## 1. 先做项目盘点（不要马上改文件）

扫描并输出一份简要盘点，包括：

- Godot 项目根目录、引擎版本（以项目文件/实际环境为准）。
- 已有文档所在位置：README、MD、TXT、TODO、开发日志、规格说明等。
- 主要游戏模块以及它们的入口脚本/场景，例如地图生成、建筑、居民、采集运输、经济人口、战斗、UI、存档等；**仅记录实际存在的模块**。
- 当前 Git 状态、知识库建议放置位置、可能需要避免的命名冲突。
- 发现的重复文档、互相冲突的说明、明显过期的记录。

**交付**：知识库中的 `90_归档/资料来源索引.md`，记下旧文档路径和用途。旧文件保持原位。

## 2. 创建知识库目录

默认在 Godot 工程根目录创建 `docs/knowledge/`。如果工程已经有清晰的文档体系，允许沿用已有目录，避免重复创建；在最终报告中说明实际位置。

```text
docs/knowledge/
├── HOME.md                       # 总入口、导航、项目概况
├── INBOX.md                      # 快速收件箱：未分类的信息
├── NOW.md                        # 当前焦点：最多 2–3 个并行任务
├── 10_设计/
│   ├── 建筑系统.md
│   ├── 居民与岗位.md
│   ├── 资源与物流.md
│   ├── 经济与移民.md
│   ├── 战斗与训练.md
│   ├── 地图与资源生成.md
│   └── 其他系统索引.md
├── 20_任务/
│   ├── Bug.md
│   ├── 待办.md
│   └── 已完成.md
├── 30_资料/
│   ├── Godot.md
│   ├── Blender.md
│   ├── 美术参考.md
│   └── 开源项目.md
├── 40_未来/
│   └── 想法池.md
├── 50_决策/
│   └── 设计决策记录.md
└── 90_归档/
    └── 资料来源索引.md
```

**避免空文档泛滥**：可先创建目录、核心四文件（`HOME.md`、`INBOX.md`、`NOW.md`、`40_未来/想法池.md`）和实际有可靠内容的系统文件。其他文件按需创建，不强制一次全部填满。

## 3. 分类和迁移规则

把找到的记录归入以下类型。可在新文件中摘要并链接来源，**不要直接搬走或删除原件**。

| 类型 | 判断标准 | 目标位置 |
|---|---|---|
| 当前任务 | 已决定近期实际执行，有明确完成条件 | `NOW.md`、`20_任务/待办.md` |
| Bug | 可描述异常、预期行为和复现方式 | `20_任务/Bug.md` |
| 正式设计 | 已经讨论确定或已被工程实现的规则 | `10_设计/` 对应文件 |
| 设计决策 | 重要方案选择、舍弃方案及原因 | `50_决策/设计决策记录.md` |
| 未来想法 | 尚未决定实现时间或条件不成熟 | `40_未来/想法池.md` |
| 资料链接 | 教程、插件、GitHub 项目、美术参考 | `30_资料/` 对应文件 |
| 历史材料 | 已替代但需要保留的旧方案/旧文档 | 保留原件，并在来源索引中标注 |

### 冲突处理

如果同一系统的资料出现互相矛盾的规则：

1. 优先以当前工程**实际行为和代码结构**描述“当前实现”，但不要据此推断它一定符合设计意图。
2. 另列“文档中的目标设计”及其来源。
3. 在“待确认”中指出差异；**不要擅自决定哪份需求应被删除**。
4. 给出建议的确认问题，供用户审核。

### 去重处理

按“主题 + 当前结论”合并重复摘要；保留各来源路径。不要因为两个文件名字相似就判定内容相同。

## 4. 文档格式规范

### 4.1 系统设计文档统一模板

```md
# 系统名称

- 设计状态：草案 / 已确定 / 待确认
- 实现状态：未开始 / 部分实现 / 已实现（待测试） / 已验证
- 最后核对：YYYY-MM-DD
- 主要来源：`res://...` 或仓库相对路径

## 当前实现
只描述能够从工程验证的现状。

## 目标设计
只描述现有文档或已确认的规划；不凭空补需求。

## 关键规则与流程
以简短条目记录规则、触发条件、输入输出和例外。

## 关联模块
列出相关脚本、场景和其他设计文档的链接。

## 待确认问题
- [ ] ...

## 设计决策与变更记录
- YYYY-MM-DD：变更内容、原因、来源。
```

### 4.2 Bug 模板

```md
## BUG-001 简短标题
- 状态：待复现 / 待修复 / 修复待验证 / 已解决
- 严重性：阻塞 / 高 / 中 / 低
- 影响系统：
- 复现步骤：
- 实际结果：
- 预期结果：
- 相关文件：
- 来源与记录时间：
- 验证结果：
```

不确定是否还存在的问题，先标记“待复现”，不要直接宣布已经修复。

### 4.3 想法模板

```md
## IDEA-001 想法标题
- 所属系统：
- 一句话描述：
- 价值/解决的问题：
- 前置条件：
- 状态：仅记录 / 待评估 / 已纳入版本 / 放弃
- 来源：
```

不要为了填模板而编造信息；未知可以留空。

## 5. 先行重点核对的系统

按仓库中真实存在的代码和文档逐个核对，优先关注：

1. **居民与岗位**：状态机、自动分配/辞退、待命、采集预约。
2. **资源与物流**：伐木、背包容量、工作建筑仓储、送回据点。
3. **建筑与蓝图**：建筑分类、等级 T0–T3、建造、升级及插件配置的实现状态。
4. **经济与移民**：住房、人口、谷物/肉类/精致食物需求、需求刷新。
5. **战斗与训练**：基础战斗能力、民兵营、兵种分支、训练流程。
6. **地图系统**：程序化地图、模块拼接、地形区域、资源生成、导航。
7. **其他系统**：仅记录仓库内确有证据的功能。

**重要**：上述条目是“核对主题”，不是已经实现的功能清单。例如“民兵营升级到火炮营”如果仅在规划中出现，不得写成已开发。

## 6. 生成项目主页与当前工作页

### `HOME.md` 应包含

- 项目一句话定位（若资料不足，标为待确认）。
- 当前开发阶段（有证据才填写，否则待确认）。
- 常用入口：收件箱、当前任务、Bug、设计目录、未来想法、资料库、决策记录。
- 核心系统状态表：系统、设计状态、实现状态、文档链接、待确认数。
- 最近重要决策（只引用已有的确定信息）。
- 资料可信度说明：`工程已验证 / 文档已确认 / 待确认`。

### `NOW.md` 应包含

- 本周主要目标（若用户没有明确目标，写“待用户确认”，可列建议但不能当作已定事项）。
- **同时进行的任务不超过 3 项**。
- 每个任务：目标、完成条件、相关设计文档、阻塞问题。
- “下一次打开工程先做什么”。
- 不在当前范围的功能指向想法池。

## 7. 建立日常低维护流程

**随手记录（随时，10 秒）**

- 新想法 / 新 Bug / 教程链接先追加到 `INBOX.md`。
- 允许用一行文字，无须立刻分类。

**每天开发结束（约 5 分钟）**

- 将 Inbox 新增记录分流到任务、Bug、设计、资料或未来想法。
- 更新 `NOW.md` 的“下次首先做什么”。
- 确认本日已修复的 Bug 是否经过验证，未验证保持“修复待验证”。

**每周复盘（约 15 分钟）**

- 合并重复记录、标注失效链接或旧方案。
- 核对设计文档与实际工程差异。
- 决定下周 2–3 个重点；其余保持待办或想法状态。

**每次 GPT 讨论结束**

让助手输出：
1. 本次确定的决策；
2. 需要更新的既有 MD 文件与具体增量；
3. 新增待办、Bug 和待确认问题；
4. 不应进入当前开发范围的灵感。

仅在读取相关原文件之后合并修改，且保留原有重要决策与来源。

## 8. 可复用的客户端执行步骤

请按下面顺序完成：

### 阶段 A：只读审计
- [ ] 确认工程根目录和 Git 状态。
- [ ] 找出已有文档及代码主模块。
- [ ] 汇总已实现与已规划功能的证据。
- [ ] 列出重复、过期、相互冲突的信息。

### 阶段 B：创建框架
- [ ] 创建 `docs/knowledge/` 及需要的目录。
- [ ] 创建 `HOME.md`、`INBOX.md`、`NOW.md`、`40_未来/想法池.md`。
- [ ] 创建来源索引并链接到已有文档。

### 阶段 C：分批整理
- [ ] 先整理居民/资源物流，再整理建筑/经济/战斗，最后整理地图等其他模块。
- [ ] 只在有足够资料时建立具体系统文档。
- [ ] 提取现有 Bug、待办、参考资料，不自行杜撰。
- [ ] 将重要已知设计取舍追加到决策记录，并注明依据。

### 阶段 D：交叉检查
- [ ] 所有文档内部链接有效。
- [ ] 没有误将未来计划写成已实现。
- [ ] 没有覆盖或删除用户原文档。
- [ ] 未修改任何游戏运行文件。
- [ ] `HOME.md` 可以导航到所有新知识库文件。
- [ ] 没有大段复制代码或无意义的空模板。

### 阶段 E：最终报告

最终回答用户时，请包含：

1. **实际创建/更新的文件列表**及其路径；
2. **本次梳理的主要系统**与发现的实现状态；
3. **需要用户确认的设计冲突**，按重要性排序；
4. **未能确认的功能和信息缺口**；
5. **建议下一步整理的事项**（最多 3 项）；
6. **明确声明是否修改了游戏源代码**，如有意外改动必须说明。

## 9. 本次任务的完成标准

- 打开 `HOME.md`，无需翻聊天记录即可找到当前工作、系统设计、Bug 和未来想法。
- 任意一条重要信息都能找到来源或被明确标为“待确认”。
- 有效区分**实际工程现状 / 确定的目标设计 / 尚未决定的想法**。
- 原始资料和游戏代码均保持安全、不丢失。
- 日常维护只需要收件箱、当前工作页和少量定期复盘。

## 可直接交给客户端的任务指令

> 请阅读本执行计划，在当前 Godot《时间裂缝》工程中搭建和整理 `docs/knowledge/` 知识库。先只读扫描项目与现有文档，再按阶段逐步创建索引、归纳实际已实现系统、汇总规划与待确认事项。不要修改游戏代码、场景、资源、插件；不要删除或覆盖现有文档。每条重要结论需可追溯到现有文件，无法核实的标记为待确认。优先完成可用的 HOME / INBOX / NOW / 想法池，不要为了齐全创建大量空文档。最后提交文件变更清单、发现的冲突和最多三个后续建议。
