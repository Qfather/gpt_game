# 工程优化审查（2026-10-09）

本轮检查主场景、居民与敌人、驻军、任务和人口管理、资源生长、道路与导航、战争迷雾、HUD／建筑提示，以及地图和渲染配置。只做审查和隔离诊断，没有修改正式游戏代码。不是逐个美术资源的 GPU 分析，也不是完整40分钟关卡验收。

## 建议顺序

| 优先级 | 项目 | 当前证据 | 建议与验证 |
| --- | --- | --- | --- |
| 1 | 普通过程日志 | 当前33居民／15敌人／3倍速对照：开启普通输出持续战斗平均286.83ms；仅在诊断进程关闭普通输出为17.86ms。改用原生文件重定向的敌袭阶段仍268.76ms，排除了仅由 PowerShell 收集造成的解释。 | 战斗、工作、状态切换日志按调试开关／等级输出，格式化也放在开关内；错误和必要警告保持输出。收益需在编辑器启动与正式导出中分别复测，不能直接承诺原第19分钟现场已解决。 |
| 1 | 驻军分配及人数查询 | `barracks.gd::_process()` 每帧分配；`dispatch_available_swordsmen()` 对每名居民调用空位查询，空位查询最终进入 `get_garrison_count()` 再遍历全体居民。空塔无合适弓箭手时可形成每塔每帧人口平方量级的检查。箭塔迷雾视野查询也调用这段人数修复逻辑。 | 新军人产生、空位释放、军营建成时请求分配；一次分配先整理名单并计算空位。查询人数只读取维护好的名单，旧状态自修复单独低频执行。验证空塔／满塔／多塔、训练完工、需求中断和预约不超员。当前压力场景未配置箭塔，收益需增加多塔对照实测。 |
| 1 | 迷雾 CPU 刷新尖峰 | 当前代码已有静态视野、角度、像素和对象子节点缓存；仍每0.1真实秒集中合并所有移动视野，扫描对象显隐。移动角色越多，缓存失效越多。 | 先给静态对象建立空间分区，只更新视野变化覆盖的区域；保留动态单位及时显隐。再评估把纯像素合并移到原生代码，或将纯视觉遮罩放到 GPU；游戏可见性仍保留 CPU 数据。需跑像素等价、树冠遮挡、昼夜、对象增删和渲染测试。不能仅凭圆形半径重叠就删除视野源，树木遮挡可能不同。 |
| 2 | 敌人和战斗单位决策扫描 | `enemy_base.gd::_process()` 每渲染帧重新扫描居民与敌人；普通居民已经不再主动搜敌，室内避难也已改为共享警报。 | 战斗单位保留当前合法目标；死亡／失效立即处理，完整重新选敌可尝试约0.1–0.2真实秒、按单位错开。先做距离平方筛选，再执行职责等较贵判断；人数进一步增加时再用共享空间分区。攻击冷却和移动仍按原物理流程执行。验证优先攻击军人、维修工、阵营、隐藏目标和目标死亡；决策节流有相应反应延迟，需要试玩确认。 |
| 2 | 找资源及失败重试 | `find_nearest_resource()` 遍历资源，遇到更近候选就调用 `get_gather_position()`；每次最多执行8条路径查询。无资源时也可能反复回工作点、重新搜索。 | 先筛选并按距离排序，再逐个验证最近可达资源，找到即可停止；失败结果短期缓存，资源成熟／预约释放／导航变化时失效。无工作进入等待，避免反复切换状态。验证绕障、资源预约、满仓运输和资源再生。 |
| 2 | 集中重规划及导航几何收集 | 建筑／资源变化合并后异步烘焙已实现，不能再当作同步烘焙问题。仍需收集全场静态碰撞，并在导航迭代变化后触发居民路径更新。`get_debug_mesh().get_aabb()` 也在几何收集中重复使用。 | 缓存静态障碍轮廓，变化时失效；对路径重规划设置预算、错开单位；失败入口查询按导航版本及建筑状态短期缓存。先测大量清障／连建城墙时的烘焙次数和主线程几何收集耗时，再考虑分区导航。保留真实实体绕障，不通过取消墙体碰撞提速。 |
| 3 | 人口、HUD 和血条重复刷新 | PopulationManager 每帧重算人口及住房；HUD 每帧分别扫描空闲、居民、剑士、弓箭手人数。血条同时响应信号并每帧重算数值；室内提示每帧重新归类和布局。 | 人数在增删、职业、职责、进出屋事件后更新，变化即时刷新，包括暂停操作；相机移动时只更新屏幕位置，进度条保持必要刷新。不能用统一低频定时器代替玩家操作后的立即反馈。验证暂停解雇、训练转换、死亡和相机移动。当前小规模测量中 HUD 本身收益较低。 |
| 3 | 资源变化唤醒所有运输居民 | TaskManager 每次库存变化都遍历全体居民调用 `wake_delivery_task()`；调度本身有 deferred 合并，但这次遍历发生在合并之前。 | 合并同帧资源事件，按资源类型维护正在等料的任务／居民，只唤醒相关等待者。验证材料到货、取消任务、资源预约和满仓运输不漏唤醒。 |
| 3 | 受击表现 | 受击闪白每次创建材质、遍历子网格，并给每个网格创建恢复定时器。 | 闪白材质复用、外观网格缓存、每角色一个恢复流程。关闭普通输出后的现有战斗流程耗时已明显降低，暂没有证据将受击表现排到日志之前；先拆分材质和定时器成本，再决定是否需要池化。 |
| 后续 | 静态场景渲染及启动 | 当前压力场景约1.1万节点、上千次绘制调用、约200万绘制图元；旧启动记录已确认首帧渲染准备仍有波动。地形查询、资源外观模板、道路分块已有优化。 | 先测 CPU／GPU 各自耗时；草与重复装饰按区域做 MultiMesh，保留可采集资源的独立逻辑、拾取及迷雾；检查模型材质／表面数量、LOD、阴影和海面网格。大规模合并会影响单体剔除，必须分区。优先试一小块树林，不直接重写全部资源系统。 |

## 不建议先做的事

- 不先重写居民全部状态机，也不因 `villager.gd` 接近5000行就判定它必然慢；优先处理具体重复查询，再按行为提取已验证模块。
- 不用降低人数上限、关闭迷雾或改物理补帧上限代替定位。
- 动态单位避让和建筑／城墙实体碰撞是不同成本。若允许轻微单位穿模，可以单独试停用动态避让；也可先把当前0.425米探测半径和退让阈值匹配实际居民碰撞尺寸。需确认窄路、敌人接近和拥堵不会恶化。当前版本的实际收益以重新计时为准。
- 资源成熟恢复碰撞后已经 `set_process(false)`，不需要再对成熟树木增加一套停更机制。
- 道路查询已经有每物理帧2次预算、导航目标变化阈值，以及成功查询后的重试间隔；优化应先测复杂道路网络，不能把它说成毫无限制的每帧寻路。

## 当前版本带画面诊断

使用 Godot4.7.2、Forward+／D3D12、GTX1650，固定种子418、33居民、15敌人、3倍速。按顺序运行独立进程，保留 AI、碰撞、采集、受击和渲染；没有关闭用户已有编辑器。

| 阶段 | 普通输出开启平均／P95 | 普通输出关闭平均／P95 |
| --- | --- | --- |
| 正常工作 | 46.93／83.58ms | 13.90／35.00ms |
| 敌人到场 | 297.04／447.30ms | 16.38／36.50ms |
| 持续战斗 | 286.83／422.75ms | 17.86／39.86ms |
| 随后冻结迷雾 | 263.43／426.25ms | 13.28／18.76ms |
| 再绕过动态避让 | 259.91／391.05ms | 13.34／16.56ms |
| 再冻结单位 AI | 13.26／13.66ms | 13.32／13.61ms |

关闭输出只发生在 `.godot/project_review_quiet.gd` 诊断子类，使用 `Engine.print_to_stdout=false`，保留错误输出。正式代码和工程设置未改变。两轮六阶段均完成，人数始终符合预期，孤立节点监视值0，错误日志为空。

额外换成 `cmd.exe` 原生重定向，开启普通输出的正常工作18.27／47.26ms、敌人到场268.76／392.25ms，说明战斗慢帧不限于 PowerShell `Start-Process` 的收集方式。该核对在取得敌袭数据后结束，保留部分阶段结果，不算一轮完整六阶段测试。

关闭普通输出的持续战斗：迷雾单次刷新平均23.31ms；敌人选敌约2.96ms／渲染帧，居民搜敌计时为0，动态避让约0.25ms。这组当前布局中，普通居民重复搜敌已经消失，避让也不是首要热点。停止迷雾后平均帧时约13.28ms，支持下一步处理迷雾尖峰。

这是固定种子的独立运行，不是同一时刻存档重放；采集、碰撞及战斗状态会不同，日志开关也会影响物理补帧次数。阶段顺序、计时包装和75Hz显示器限制仍适用。约56FPS是本轮关闭输出的持续战斗均值，不能据此承诺人数上限或所有地图的帧率。没有复现用户原始19分钟现场，没有测完整关卡的长期泄漏或独立 GPU 时间。

## 官方资料核对

- [Godot 导航性能](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_optimizing_performance.html)：减少重复路径查询、错开重新规划、使用简单碰撞几何并后台烘焙。现有工程已实现其中部分措施。
- [Godot MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)：批量绘制可减少提交成本，但单个实例不能独立做视锥剔除，应按区域拆分；页面标注尚未完整更新到4.7，实际能力需用本工程验证。
- [Godot 3D 性能](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)：按场景检查可见性和渲染负载，避免只凭多边形数量判断最终瓶颈。
- [Godot Engine 输出开关](https://docs.godotengine.org/en/4.4/classes/class_engine.html)：关闭普通输出会影响控制台、日志文件和编辑器输出；错误输出由另一个开关控制，本轮没有关闭错误。
