### 每天收工

1. 用户表示收工后，助手核对当天实际改动，更新日志中的助手总结与验证遗留；保留用户填写的复盘和明日计划。
2. 核对游戏配置并运行`python docs/workbench/update_data.py`，同步数据.md的配置快照区。没变化的数值不改写，核对日期随当次检查更新；不要凭旧文档猜数值。
3. 有规则、任务或设计变化时同步系统、任务、决策；不能把代码已写当成试玩通过，验证写明方式、范围、结果和剩余边界。
4. 用户进入网页阅读、补充复盘并确定明日任务。没有记录的工作不编造，旧失败未复现则标明待核查。

### 条目格式

任务、日记和数据实体使用二级标题、稳定ID及record元数据，正文子标题从三级开始。元数据只用单行字符串、数字或布尔值；特殊字符串使用JSON双引号转义。

```markdown
## 标题 {#task-002}

<!-- record
kind: task
id: TASK-002
status: 待安排
verification: 未验证
-->

### 目标与范围
### 验收条件
### 验证记录
```

任务／问题必须有kind、id、status、verification；进度使用待安排、进行中、待验收、已完成、阻塞、取消。验证独立使用未验证、通过、部分通过、失败。日记kind为journal，有date字段和助手总结、我的复盘、验证与遗留、明日计划四栏。
新想法写入参考.md，kind为idea，ID使用IDEA编号，状态为待考虑、暂缓、已实现或取消。工作台只显示尚未实现且未取消的记录；新增想法不等于安排开发任务。
想法使用idea_group字段记录大类，同一大类下可有多个想法条目。大类是制作规划的归组，不改变游戏配置分类。

### 数据与关联

数据.md快照区覆盖data目录配置资源，并读取资源关联的导出脚本默认值和子资源；表达式保留原文，不执行GDScript。单位对比使用基础生命、伤害、间隔、射程和移速，不代表实战收益。关卡倍率、实例状态、场景专属业务参数或复杂计算未完全解析；手工知识说明写在快照区外。

每个实体标明来源、核对日期；实际资源引用和训练配方生成MD锚点关联。知识分类不自动成为游戏运行标签，未知值不能用0代替。网页编辑数据说明不会修改Godot数据；自动快照条目只读，更新须以工程配置为依据。

### 写入与历史

网页保存条目时合并回所在主文件，检查整份文件的原文哈希；外部修改时拒绝覆盖，保留草稿供手动合并。旧版本在workbench/.history，Git由用户主动提交上传。每日新增记录追加到日志.md，不再新增日记文件；多年日志需要拆分时再归档。

归档保留原文与原目录结构，默认只读。移动约束原文见[归档](归档/移动与导航约束.md)，它仍是相关开发的有效约束，归档不等于规则失效。
